# ECAI: compute-provider accounts, bounded reservations and NFT review

This rebased implementation adds **Compute & NFTs** to `/dashboard#compute`, reusing DamageBDD
login/bearer authentication and the ECAI dashboard styling. It can be integrated later with the separately delivered one-shot remote
worker starter; that worker is not included in this patch.

## Guided click-through connection (October 2026 UI update)

The **Compute & NFTs → Provider accounts** view now starts with a provider
picker. Only the selected provider's setup steps are expanded; configuration
fields remain inside an editable **Enter existing resources** section.
External console links use fixed AWS/Google Cloud origins and open in a new
tab. For Google Cloud, entering a valid project ID updates links to Cloud Run
Jobs, IAM workload identity pools, service accounts and GCS buckets. Invalid
or blank project hints are discarded rather than reflected into URLs.

The steps are **Choose → Delegate access → Verify identity → Continue to
budgets**. Identity verification is still **not** cloud execution or OAuth
account authorization. There is no implicit cloud billing consent and no
credential-upload or wallet-signing step in this onboarding.

### AWS: prepare first, then create the IAM role

1. Select **AWS Batch → Generate setup ID**. This calls authenticated
   `POST /ecai/compute/providers/aws_batch/prepare` with `{}` and persists a
   new, account-scoped 48-character hex external ID in DETS. It generates the
   ID **before** all resource fields are supplied. Repeating the request,
   restarting the node or updating the AWS connection does not rotate it.
2. The ECAI operator configures its precise **coordinator IAM role ARN** in
   `sys.config` (or other application environment):

   ```erlang
   {ecai, [
       {compute_aws_coordinator_role_arn,
        "arn:aws:iam::210987654321:role/EcaiCoordinator"}
   ]}.
   ```

   Only IAM role ARNs pass server-side validation. The browser cannot edit
   this principal and **will not construct a trust policy without one**.
   Never trust `*` or an entire external AWS account implicitly.
3. Click **Copy trust policy** to copy scoped JSON with the exact operator
   principal and per-account `sts:ExternalId` condition. Click **Open AWS IAM**,
   create a role using **Custom trust policy**, and attach narrowly scoped
   Batch (`SubmitJob`, `DescribeJobs`, termination if needed), S3 and optional
   KMS permissions as appropriate. Independently provision the Batch queue,
   immutable job definition and tenant-specific S3 prefix.
4. Expand **Enter existing AWS resources**, paste the role ARN, queue,
   job definition, region and bucket. Save, then **Verify IAM role access**.
   The ECAI coordinator's AWS CLI calls STS AssumeRole without returning
   temporary credentials to the browser.

A generated external ID does not create an AWS identity or IAM role. This is
an IAM-console handoff, **not** a one-click CloudFormation deployment.

### Google Cloud: console deep links, not a copied JSON key

1. Select **Google Cloud Run Jobs**. Enter your project ID in the first step
   to open Cloud Run Jobs and GCS directly in that project.
2. Open the workload identity pools and service accounts links. The ECAI
   node operator must provision or authorize a trusted federation source
   (for example an OIDC workload identity provider) or node-managed
   short-lived credentials. Configure scoped Cloud Run and GCS permissions.
3. Expand **Enter existing Google Cloud resources**, enter the existing job,
   region, bucket and worker service account, save, then click **Verify Cloud
   Run visibility**. This invokes `gcloud run jobs describe` on the server.

These links do **not** complete an OAuth browser redirect or deploy a Cloud
Run job. Fully automated cloud provisioning would require a separately
reviewed and consented integration, such as an AWS CloudFormation template or
Google Cloud OAuth plus organization-specific IAM federation provisioning.

The onboarding API requires the same explicit authenticated bearer token as
other compute writes. The pre-created external ID is a non-secret trust
condition; it is owner-scoped and never included in provider deep-link URLs.

## Shipped in this rebase

- Per-account AWS Batch / Cloud Run configuration (no static cloud keys)
- AWS trust `external_id` generated by the ECAI node, stable across updates
- Identity verification via installed `aws` or `gcloud` CLI, using node identity
- Owner-scoped, DETS-persisted budget and mint settings, with explicit
  `remote_enabled` opt-in independent of entering a budget
- Server-generated price-ceiling quote, integer-cent reservation and idempotency
- Owner-only reservation cancellation before dispatch and no billing by reserve
- Eligible NFT list from **existing** `ecai_index_jobs_srv` and
  `ecai_index_artifact:nft_metadata`, with manual mint-review intent and fee cap
- Read-only dashboard showing reserved allowance, no fabricated actual charges
- Explicit bearer token for mutation operations (prevents ambient-cookie CSRF)

**Not implemented yet:** actual AWS Batch/Cloud Run submission, cloud invoice
reconciliation, wallet connection/signature, chain transaction submission,
NFT token ID/transaction confirmation, royalty accounting and tax settlement.
Connection verification tests identity, **not permissions for execution**.
A successful reservation has status `awaiting_dispatch` and does not launch a
container. An NFT request has status `awaiting_wallet_signature` and does not
call `ecai_nft:mint_index_job/3` (that API currently makes a dry-run contract
call and is not the index-manifest minting pipeline).

To turn a reservation into real dispatch, wire it into the **trusted** shard
planner and the separately delivered remote worker, with attempt/lease
fencing, max tasks/concurrency and retries enforced on the provider API, with
SHA-256 verified artifact import before indexing success and mint eligibility.
Use provider statements to reconcile spend before releasing/settling budget.

## Installation

This update was prepared against the uploaded `latest-ecai.tar.gz`
(14 October 2026). Apply it from your DamageBDD root (which contains `apps/ecai`):

```sh
git apply --check ecai-provider-clickthrough.patch
git apply ecai-provider-clickthrough.patch
```

The rebased console keeps the Video Studio and Market Maker integrations. The
Compute & NFTs panel is rendered through `ecai_dashboard:render_dashboard_page/2`
and uses the same DamageBDD browser session. Clicking "Compute budget & NFT
settings" in Index jobs carries the currently selected source job ID to the
remote reservation form. `GET /ecai/compute/eligible-sources` supplies a
filtered list of owned shard jobs; writes remain explicit bearer authenticated.

The settings worker is enabled by default (there are no provider credentials or
remote launches by default), with zero compute and NFT budgets and both
spending/publishing toggles disabled. Set `compute_settings_enabled` to `false`
to disable the service, or configure `compute_settings_path` for durable DETS
storage. The default store is `ecai_paths:index_state_dir()/compute_settings.dets`.

For estimates, configure conservative operator price ceilings (illustrative values, **not current provider pricing**):

```erlang
{ecai, [
    {compute_price_upper_bounds, #{
        <<"cloud_run">> => #{vcpu_micro_usd_sec => 30,
                             gib_micro_usd_sec => 5,
                             fixed_micro_usd => 2000,
                             safety_basis_points => 20000},
        <<"aws_batch">> => #{vcpu_micro_usd_sec => 35,
                             gib_micro_usd_sec => 5,
                             fixed_micro_usd => 2000,
                             safety_basis_points => 20000}
    }}
]}.
```

These numbers are *example operator-configured ceilings* in micro-USD/s,
not official rates or guarantees. Include all ancillary spend (storage,
network, NAT, logs, image pulls, retries) in the conservative fixed allowance
and configure cloud-enforced quotas, billing budgets and job timeouts too.
Budget/retry ceilings must be revalidated at dispatch time; **never** rely on
this user settings service alone to bound a real cloud charge.

The default monthly and per-job limit is zero; remote indexing and mint review
are disabled independently of the limits. Saving a cloud connection resets its
verified status. No permission to spend money is granted merely by saving settings.

## Connect AWS Batch

1. Click **Generate setup ID** and copy the displayed unique `external_id`
   before creating your AWS role. Use **Copy trust policy** when the node
   operator's coordinator role ARN is configured.
2. Configure the role's trust policy in the AWS console. Trust
   **only** the ECAI operator's IAM principal as role consumer, for example:

```json
{
  "Version": "2012-10-17",
  "Statement": [{"Effect": "Allow", "Principal": {"AWS":
     "arn:aws:iam::<ECAI_ACCOUNT_ID>:role/<ECAI_COORDINATOR_ROLE>"},
     "Action": "sts:AssumeRole", "Condition": {"StringEquals":
     {"sts:ExternalId": "<DASHBOARD_EXTERNAL_ID>"}}}]
}
```

3. Save the role ARN, region, *pre-created* Batch queue and job definition,
   and staging S3 bucket from the dashboard. Allow only required `batch:SubmitJob`, `batch:DescribeJobs`,
   `batch:TerminateJob` and scoped S3/KMS operations. Use an independent
   least-privilege **Batch task role** for the worker's staging prefix.
4. Install AWS CLI and provide the ECAI *node* with its own short-lived
   federation credentials. Click **Test identity**; it calls STS AssumeRole
   without returning temporary credentials to the browser.

For AWS Batch Spot, set retries/timeout caps and use a provider-side cost
monitor: spot prices and external data transfer prevent cost guarantees.

## Connect Cloud Run Jobs

Create a pre-deployed container job pinned to an immutable image digest,
with a dedicated service identity and GCS access only to its tenant-specific
staging prefix. Configure the ECAI node's gcloud credentials using Workload
Identity Federation (preferred) or operator-managed workload credentials.
Save project, region, job, bucket and worker service-account email in ECAI.
**Test identity** calls `gcloud run jobs describe`; it is a read test, not a
permission check for `run.jobs.run` or `iam.serviceAccounts.actAs`.

Google Cloud offers eligible **spend-cap budgets** for selected project/service
scopes, but in-flight usage and some persistent resources can still accrue
charges. Configure them independently of the ECAI reservation ledger.

## Routes

| Method | Route | Action |
| --- | --- | --- |
| GET | `/ecai/compute/settings` | Scoped account config, reservations, review records |
| GET | `/ecai/compute/eligible-sources` | Owned shard source job suggestions |
| POST | `/ecai/compute/policy` | Save monthly compute/mint limits and recipient |
| POST | `/ecai/compute/providers/aws_batch` | Save role/batch connection |
| POST | `/ecai/compute/providers/aws_batch/prepare` | Persist a stable per-account external ID before role creation (empty JSON object required) |
| POST | `/ecai/compute/providers/cloud_run` | Save Cloud Run connection |
| POST | `/ecai/compute/providers/:provider/verify` | Verify node identity access |
| POST | `/ecai/compute/quote` | Estimate conservative cost for a trusted staged shard |
| POST | `/ecai/compute/reservations` | Reserve cost with `Idempotency-Key` and confirmed `expected_reserve_cents` |
| POST | `/ecai/compute/reservations/:id/cancel` | Release undisbursed reservation |
| GET | `/ecai/compute/mintable` | List ready artifacts owned by session |
| POST | `/ecai/compute/mint-requests` | Request mint review; no chain submission |

All mutations require an explicit **DamageBDD bearer token**. The owner always
comes from `damage_auth` (never from a body field). Plaintext cloud keys and
wallet signing keys are rejected as unexpected fields. API changes use
`cache-control: no-store`; persistence is per account and uses DETS.

## Lifecycle and cost semantics

```
owner signs in -> config provider -> identity check -> save limits
-> explicitly enable remote budget reservation
-> choose verified staged shard -> server quote -> explicit expected_reserve_cents -> reserve cents (durable)
-> awaiting_dispatch (NO CLOUD JOB YET)
-> [future: attempt fenced launch / billing reconciliation / artifact import]
-> existing index finalizer -> ready_to_mint
-> request mint review (explicit recipient and fee cap)
-> awaiting_wallet_signature (NO ON-CHAIN TX YET)
-> [future: wallet signature, chain submission and confirmation]
```

USD amounts are integer cents. Each reservation and mint review is tied to a
UTC month, and a future dispatcher must recheck month validity before spending.
Existing `/ecai/index-jobs` local queues are intentionally untouched; budget
policy does **not** intercept those local operations. For enforced BYOC remote
indexing, require all remote submissions to pass the reservation manager at
launch and reconciliation. There is currently no billing source and no way to
mark a reservation spent: `actual_billed_cents = null` intentionally.
